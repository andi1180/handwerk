# Valooro Handwerk

Eigenständiges Repo mit **eigenem Supabase-Projekt** (getrennt vom Hotel-Projekt). Migrationen starten frisch ab `0001` und werden **manuell** über das Supabase-Dashboard (SQL Editor) angewendet — nie lokal ausführen, nie `supabase db reset`.

Technische Doku: siehe [TECH.md](TECH.md).

## Build-History

- **Schritt 1 ✅ DB-Fundament (Migration 0001)** — 7 Tabellen, RLS, explizite GRANTs, Mandanten-Isolation, i18n-Felder, Verify-Gate.
- **Schritt 2a ✅ App-Scaffold + Supabase-Clients + i18n + CSS-Tokens** — Next.js 15 (App Router, React 19, TS strict), 3 Supabase-Clients (Browser/Server via `@supabase/ssr`, `service_role` via `@supabase/supabase-js`), typsicherer i18n-Layer (`de`), Valooro-Token-System in `globals.css`. Noch ohne Auth/Features.
- **Schritt 2b ✅ Auth + geteilter Login + geschützte Portal-Shell** — `@supabase/ssr` auf `0.12.x`, Middleware-Session-Refresh + Schutz von `/portal/*`, Login-Seite (Client, `signInWithPassword`), `getCurrentBusiness()` über authentifizierten Server-Client (RLS-erzwungen, kein `service_role`), Portal-Shell mit Sidebar + Logout, Test-Seed. Noch ohne Module/Features.
- **Schritt 3 ✅ Auftrag anlegen + Auftragsliste (manueller Pfad)** — Sidebar-Nav (Client, Aktiv-Zustand via `usePathname`) um „Aufträge" erweitert; Auftragsliste (Server Component, AUTHENTICATED Client, RLS + defensiver `business_id`-Filter, `created_at DESC`); Status-Badge-Komponente; Anlage-Formular (Client, `div + onClick`, kein `<form>`); Route Handler `POST /api/portal/orders` mit `business_id` aus Session (Isolationsregel), `status='draft'`. Mobile-first. Kein Capture/Media, keine Generierung.
- **Schritt 4a ✅ Storage-Fundament (0002) + Auftrags-Detailseite + Medien-Liste** — Bucket `order-media` (privat) + tenant-skopierte `storage.objects`-Policies (erstes Pfad-Segment = `business_id`), Verify-Gate `0002`; klickbare Auftragsliste; Detailseite (Server Component, mobile-first) mit stickyem Kopf (Kundenname + Status-Badge), Stammdaten und Medien-Liste (RLS, `sort_order` ASC, Thumbnails via server-seitiger Signed-URLs aus privatem Bucket); Query-Helper `getOrderById`/`getOrderMedia`. Reine Anzeige — kein Capture/Upload (4b), keine Generierung.
- **Schritt 4b ✅ Foto-Capture + Upload (isolations-sicher, zweistufig)** — Client-Kompression (`lib/media/compress.ts`, Canvas → JPEG, max 1500px/Q 0.8); Capture-Komponente (Client, `div + onClick`, native Kamera via verstecktem `<input capture="environment">`, Vorschau + Stichwort + Tag, optimistische In-Memory-Queue + `router.refresh()`, Storage-Upload mit 2 Retries). Zweistufig: Datei direkt in den privaten Bucket unter RLS-skopiertem Pfad `{business_id}/{order_id}/{uuid}.jpg`, Metadaten via Route Handler `POST /api/portal/orders/[id]/media` (`business_id` aus Session, Pfad-Validierung, `sort_order` fortlaufend). Detailseite bleibt Server Component. Nur Foto — Video folgt in 4c, keine Generierung.
- **Schritt 4c ✅ Video-Capture + Längen-Check** — denselben Flow wie 4b erweitert (Komponente + Route Handler, nicht dupliziert): zweiter Button „Video aufnehmen" (`<input accept="video/*" capture="environment">`); Dauer-Lesung (`lib/media/video.ts`, verstecktes `<video>` + `loadedmetadata`), `MAX_VIDEO_SECONDS = 30` — zu lang ⇒ Ablehnen (i18n `capture.videoTooLong`), kein Upload, kein Trim (MVP). Video wird **nicht** clientseitig komprimiert: Datei unverändert in den Bucket unter `{business_id}/{order_id}/{uuid}.{ext}`, Hintergrund-Queue/Retries/optimistische Liste wiederverwendet. Route Handler: `media_type ∈ {'photo','video'}`, `duration_seconds` bei Video erforderlich. Detailseite spielt Video-Items inline ab (`<video controls>`, Signed-URL). Keine neue Migration (`duration_seconds` aus 0001). Keine Generierung.
- **Schritt 4d ✅ Portal mobil-optimiert + i18n-Interpolation** — `/portal` bleibt **eine App**; das Chrome schaltet rein per Media Query (Breakpoint `max-width: 768px`). Desktop unverändert (220px-Sidebar); Mobile: sticky Top-Bar (gekürzter Betriebsname + kompakter Logout-Icon) + app-artige, fixierte Bottom-Tab-Nav (Dashboard/Aufträge, aktiv = `--gold`, `usePathname`; `PortalTabNav` teilt sich die `ITEMS` mit der Sidebar). Capture mobil-first: sticky Detail-Kopf klinkt unter die Top-Bar (`--portal-topbar-h`), große Aufnahme-Buttons (`min-height: 64px`), bildschirmfüllender Vorschau-/Stichwort-/Tag-Dialog (`.capture-draft` → `position: fixed`), vollbreiter „Neuer Auftrag", größere `.form-input` (16px → kein iOS-Zoom). `MAX_VIDEO_SECONDS` 30 → **20** (Settings-Ceiling 30). `t()` bekommt typsichere Platzhalter-Interpolation (`t(locale, key, params?)`, Overloads — ohne `params` bleibt das Leaf-Literal); `.replace()`-Stellen umgestellt. Keine neuen Features, keine Migration.

- **Schritt 5a ✅ Basis-Settings (Branding, Limits, Links, Delivery)** — erste Slice des Settings-Moduls, **keine neue Migration** (bestehende Spalten): `businesses.branding` jsonb (`primary_color`, `secondary_color`, `font`, `logo_per_page`), `businesses.settings` jsonb (`video_max_seconds`, `ig_handle`, `google_review_url`, `website_url`, `delivery_mode`), `retention_months` + `name` (Spalten). Geteilte Optionen/Grenzen/Guards in `lib/settings/options.ts`; `getCurrentBusiness` um typsicheres `branding`/`settings`/`retention_months` erweitert (jsonb → Defaults normalisiert/geclamped, kein `any`). Settings-Seite (Server Component) + Client-Form (`div + onClick`, kein `<form>`; Felder in `.card`-Gruppen: Color-Swatch+Hex, Selects, Toggle `role="switch"`, Range+Number; Client-Validierung = Server-Validierung). Route Handler `PATCH /api/portal/settings` (AUTHENTICATED, **`business_id` aus Session**, Validierung Name/Hex/Font/Delivery/Ranges → sonst 400, Update über `businesses_update`, gibt aktualisierte Werte zurück). Drittes Nav-Item „Einstellungen" (geteilte `ITEMS` → Sidebar + Mobile-Tab, Zahnrad-Icon). Video-Limit verdrahtet: Detailseite liest `settings.video_max_seconds` → Prop `maxVideoSeconds` an `capture.tsx` (Konstante nur noch Fallback). i18n `nav.settings` + `settings.*`. KEIN Logo-Upload (5b), KEIN Intro/Outro (5c), KEIN Slot-Editor (5d).
